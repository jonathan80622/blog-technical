# Startup AI investment evidence: UI-to-backend feature map

**Document ID:** DOC-UI-PROGRESS-001  
**Status:** code-grounded contract and gap register  
**Scope:** current `app/page.tsx` UI and its connected routes, evaluated against the product goal: identify AI trends that startups are investing engineering effort in. VC portfolios are a discovery heuristic for startup candidates, not evidence of growth or AI investment.

## Product outcome and evidence rules

The intended research path is:

1. Discover candidate startups from an investor's official portfolio page. Preserve the page and exact membership passage. Portfolio membership does not establish high growth.
2. Find official-domain technical writing and specific hiring postings for each company. A job ad is a hiring-demand signal; a technical account of the company's own implemented work is a technical-use signal.
3. Extract claims in the bounded AI taxonomy with exact source passages. Store them as candidates. An extraction is not an accepted finding.
4. Review each claim. Only accepted claims with matching company, source kind, and exact passage enter trend counts.
5. Compare trends by distinct company, report hiring and technical-use company counts separately, and let readers inspect original evidence and dates.

The implemented trend summary follows steps 3–5 for claims that exist: `lib/ai-signals.ts::summarizeTrends` excludes non-accepted, unsupported, company-less, and evidence-less claims; deduplicates companies per trend and signal kind; and returns evidence passages, source URLs, observation time, and publication time. `app/api/overview/route.ts::GET` supplies those results. The UI states that counts are scoped to its startup sample and do not establish spending, market share, or growth over time.

**Current limits:** there is no explicit high-growth qualification rule, no spend measurement, no market-wide denominator, and no longitudinal trend calculation. The displayed denominator is the promoted-candidate sample, not a growth-qualified population. These must not be implied by VC membership, hiring counts, or a snapshot of accepted claims.

## API/processes without current UI controls

| API/process | Current role | UI status |
| --- | --- | --- |
| `POST /api/chat` | Validates a bounded question, retrieves indexed passages, answers only from supplied context, and returns a no-match response when retrieval is empty. Provider/database failures return a generic service error. | Route is covered by backend contract tests; UI is a placeholder and never calls it. |
| `POST /api/queues/vc-discovery` | Private Vercel Queue callback; idempotently claims a queued job and starts workflow. | Server callback, not a user control. |
| `POST /api/internal/render/command`, `POST /api/internal/render/callback` | Authenticated renderer control-plane endpoints. | Not represented in current page; no connection to collection workflow is established by the UI. |
| GitHub Actions market-map enqueue workflow | Creates candidate discovery jobs from the checked-in market-map input. | External/manual preparation; Collection only dispatches already prepared jobs. |

## Acceptance boundary for browser automation

The companion [`ai-investment.feature`](ai-investment.feature) specifies current visible behavior and explicit gaps. Browser tests should assert both the visible state and the corresponding request/process. Route mocks can verify UI/API contracts only; a mocked queue or mocked durable workflow is not evidence that an external queue/provider run completed. Runtime selection and the local/hosted VC-dispatch branch are covered by unit contract tests. A complete end-to-end claim requires persisted job/source/document/claim/evidence/coverage records and accepted AI claims counted once per company, with hiring and technical-use counts separate.

### Product gaps to close before calling the outcome complete

- Define the evidence-backed “high-growth startup” eligibility rule before labeling the candidate sample high-growth.
- Ensure technical and hiring signal collection can be reviewed at scale; current Claims view is capped at 100 recent claims.
- Add evidence version/observation detail and stable links to inspect retained source snapshots, not only external canonical URLs.
- Playwright covers each current user action's request and visible result, including success, pending, empty, and failure states. Route mocks verify the browser/API contract only; they do not prove a real queue, workflow, or external provider run.
- Validate an actual queue/workflow/provider run separately from browser mocks and source-level tests.
